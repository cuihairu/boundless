# FantasyDemo quick start

FantasyDemo is the reference revision's bundled game: five entity types, a set of
Base/Cell/Client scripts and enough content to log in, create a character, enter
a space, move, see nearby entities, talk to an NPC and log back in. It is the
acceptance target for the login and world-entry paths.

::: warning Not in the working tree yet
`fantasydemo/` does not exist in the Boundless repository. The target location is
`examples/fantasydemo/`, tracked by **BW-14** (`todo.md`). Everything below is
quoted from the reference revision at the source commit recorded in `todo.md`;
the paths given are paths *in that revision*, not in this tree.
:::

## The five entity types

The demo registers exactly five client/server entities
(`fantasydemo/res/scripts/entities.xml`):

```xml
<root>
<!-- Generated by scripts/generate-fantasydemo-assets.py -- do not edit. -->
	<ClientServerEntities>
		<Account/>
		<Avatar/>
		<Guard/>
		<Space/>
		<ClientOnly/>
	</ClientServerEntities>

	<ServerOnlyEntities>
	</ServerOnlyEntities>
</root>
```

::: tip The generated header comment is not strict XML
The generator emits its "do not edit" banner as an XML comment, but the banner
itself contains `--`, which the XML grammar forbids inside a comment. A strict
parser therefore rejects the file (`xml.etree` reports `not well-formed` at
line 2, column 59). BigWorld's own reader accepts it, and the entity list above
is the content that matters; keep the banner out of anything you re-emit.
:::

| Type | Purpose |
| --- | --- |
| `Account` | login proxy; holds the player name and the chosen character |
| `Avatar` | the player's in-world entity (Base + Cell + Client) |
| `Guard` | a simple NPC with a patrol |
| `Space` | an in-game area with spawn points |
| `ClientOnly` | a purely client-side entity used by the client examples |

The definitions live in `fantasydemo/res/scripts/entity_defs/` — one `.def` per
entity type (`Account`, `Avatar`, `ClientOnly`, `Guard`, `Space`) together with
`alias.xml` in the same directory. There is also `res/scripts/db.xml` and
`res/server/bw.xml`.

Entity type ids are assigned in load order, starting at `0`, with `0xFFFF` as
the "no type" sentinel. That is exactly what
`crates/entitydef/src/entities.rs` already implements
(`FIRST_ENTITY_TYPE_ID = 0`, `INVALID_ENTITY_TYPE_ID = 0xFFFF`), so the loader
that will read these `.def` files has its id space fixed.

## Layout

```
fantasydemo/
  res/scripts/
    entities.xml
    db.xml
    entity_defs/            # one .def per entity type, plus alias.xml
    base/                   # Account.py, Avatar.py, Guard.py, Space.py
    cell/                   # Avatar.py, Guard.py, Space.py
    client/                 # Account.py, Avatar.py, ClientOnly.py, Guard.py, Space.py
  res/server/bw.xml
  web/php/                  # the reference's web login
```

All of these files are machine-generated — every one ends with
`# Generated by scripts/generate-fantasydemo-assets.py -- do not edit.` — and
they use **tab** indentation.

## A real script: `base/Account.py`

```python
"Account base entity: logon proxy; no cell part."

import BigWorld


class Account( BigWorld.Proxy ):

	def __init__( self ):
		BigWorld.Proxy.__init__( self )

	def onClientDeath( self ):
		self.destroy()

	def chatMessageFromCell( self ):
		pass
```

Two things about this file are worth knowing before you write your own scripts:
`Account` derives from `BigWorld.Proxy` because it has no cell part, and
`onClientDeath` is the hook that turns a dropped client into a destroyed entity.
See [Entity scripting](/guide/entity-authoring) for the full callback list and
the script-to-`.def` contract.

## The flow, and what each step should look like

| Step | Target `todo.md` item | Observable result |
| --- | --- | --- |
| Load entity definitions and config | BW-14-01-01 | the five types above parse and get ids |
| Log in and create a character | BW-14-01-02 | callbacks fire and the character persists |
| Enter, move, AOI | BW-14-01-03 | observation events for the same trajectory |
| Guard and Space scripts run | BW-14-01-04 | NPC behaviour matches the baseline |
| Log out, log back in | BW-14-01-05 | position and properties read back |
| Generated resources registered | BW-14-01-06 | every asset traceable to a source |

The reference client prints one line a second once connected, counting up,
followed by a cell-originated chat line. That sequence — client callback → Base
method → Cell entity created → cell→client method — is the same sequence the first client SDK
check will use.

## What you can run today

Nothing in this list runs against the Boundless server yet: there is no login
protocol, no Python host and no FantasyDemo resource tree in this repository.
What you *can* run today is the role binary and the config loader:

```bash
cargo test -p server-runtime          # bw.xml chain, tick, timers, signals
./target/debug/boundless-server loginapp
```

The FantasyDemo path becomes runnable as BW-14 lands; this page will then show
the real commands against `examples/fantasydemo/` instead of the reference
revision's.
